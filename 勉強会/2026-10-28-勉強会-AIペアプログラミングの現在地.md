# Part 1　世の中の動向

AIペアプロは「補完」から「エージェント」へ

---

## 「ペアプロ」の意味が変わった

IBMで開発する @TejasKumar_ の整理 (57リプライの議論に)

- **Level 1: 手書き**「もう誰もやってない (笑)」
- **Level 2: エージェントと1対1**
  Claude Code / Codex に頼む → 作らせる → 人がレビュー → 出荷
  - 発展形: *スペック駆動*。仕様やPRDを渡し、AIに質問攻めにさせてから実装させる
- **Level 3: 複数エージェントの並列運用** (worktree・tmux・タスクボード)

> IBM Technology: 「人間同士のペアプロと同じで、人間とAIの**両方が能動的に関わるときだけ**うまくいく」

---

## 利用の広がり

- JetBrains開発者調査 (2026年1月、1万人超) <span class="tag amber">二次情報</span>
  - 仕事で使うツールは **Cursor 18% ／ Claude Code 18%** で並ぶ
  - 満足度は Claude Code がトップ
- よくある構成は **2本立て**
  - IDE型エージェント (対話しながら) ＋ ターミナル型エージェント (任せきり)
- **採用面接**にも広がっている
  > 「1次面接から、相手のコードベースでAIエージェントとのライブペアプロを求められた。フィードバックでは、**AIの使い方が不合格の一因**だった」(@ryanaidilp_, 202 likes)

---

## 実績①: Claude Codeチームは、コードの約9割をAIが書く

HN **487pt ／ 481コメント**「How the Claude Code team does code review」(10/15) <span class="tag green">一次情報</span>

- Claude Code のコードの **約90%を Claude が書く** → レビュー体制を作り直した
- 目標は *人のレビュー時間を減らし、revert や障害は増やさない*
- 方法は **何層ものレビュー**
  - 先に自動レビュー層を通す (全PRでAIがレビュー)
  - 人間はリスクの高い判断に集中する
  - コア部分の変更は、今もコードオーナーの承認が必須

---

## 実績②: エージェントにIDEの「知能」を渡す

@jetbrains (10/26): **Netflix** の事例 <span class="tag amber">二次情報</span>

- JetBrains IDE のコード解析エンジンを **headless で** エージェントに渡した
- Java/Kotlin の実タスクで **効率が20〜30%向上** (トークン数・所要時間)
- **正確性は落ちていない**

<br>

> 学び: grep だけでなく、型・参照・依存関係を正しくたどれる**道具**を渡すと、エージェントの迷いが減る

<p class="note">※ JetBrains関係者による投稿。Netflixの一次資料は未確認</p>

---

<!-- _class: dense -->

## 逆風:「コードは増えたが、ソフトウェアは増えない」

HN **365pt ／ 314コメント** (Ars Technica, 10/13)
Harvardのワーキングペーパー: 718社、3億件の作業イベントを分析

| 指標 | AIエージェント導入後の変化 |
|---|---|
| コード量 | **+30%** |
| 完成した成果物 | 統計的に有意な増加なし |
| PR提出からマージまで | **+49%** (平均7.0日 → +3.5日) |
| レビューに関わる人の割合 | +14% |

> 論文の要旨:「生産性の向上は、ソフトウェアの産出や雇用の変化に**そのままは**結びつかない」

---

## つまり: ボトルネックが「書く」から「レビュー」へ移った

```
Before : [考える] → [書く ■■■■■■] → [レビュー ■]       → マージ
After  : [考える] → [書く ■]       → [レビュー ■■■■■■] → マージ
```

- 生成が速くなるほど、**レビュー待ちの列**が伸びる
- 成果が出ている組織 (Claude Codeチーム) は、**レビュー側を仕組みとして作り直した**
- 導入して効果が出るかどうかは、*検証とレビューの設計* で決まる

# Part 2　実績のあるプラクティス 7選

---

## ① いきなり書かせない: Plan → Spec → 実装

- 最初は **Plan mode** から (Claude Code作者の公開アドバイスのまとめ, @FarhanRakhangi)
- **スペック駆動開発 (SDD)** が広がっている
  - GitHub *spec-kit*: 仕様・計画・タスクのテンプレートをエージェントに渡す
  - AWS *aidlc-workflows*: 開発工程ごとのステアリングルール (HN 28pt)
  - 仕様の**受け入れ条件 → テスト**に変換し、エージェントにそれを通させる
- 小さく区切る
  > 「ゲームを丸ごと作らせない。小さな世界を1つ渡して、**1つのシステムずつ**改善させる」(@Kristal68836455)

---

## ② コンテキストはリポジトリに置く

- **CLAUDE.md / AGENTS.md を git で管理**し、チームで共有する
- **AIがミスしたら、ルールに1行追記**する (作者ワークフロー:「Every mistake becomes a rule」)
- OSSでも普及: **SDL の CLAUDE.md** がHNで話題 (10/27)
- 注意: 詰め込みすぎは逆効果
  - 「CLAUDE.mdに何百行もプロンプトを書いていない?」上級者は積み増す代わりに、*シニアの習慣を標準として仕組みにしている* (@Yarad_ai)
- 設計の質 (SOLID・パターン) をどう守らせるかは、まだ議論が続いている (@gum49073, 16リプライ)

---

## ③ AI自身に検証させる: テストとフック

> 「CLAUDE.md は**助言**。見落とされることもある。フックは条件を満たせば**毎回必ず**実行される」(Kaif Kohari)

- **フックでTDDを強制する** (aalonso.dev, 10/24)
  - テストを先に書かせ、*テストを通す分だけ* 実装させる → **作業範囲の膨張も防げる**
  - 「TDDしてくれていると思い込んでいたが、実際はしていなかった」という気づきが出発点
- **Make Claude verify its work**: 完了前にAI自身に検証させる (作者ワークフロー)
- 関連OSS: reticle (エージェントの自己検証, Show HN)

---

## ④ レビューを多層にする

- **AIレビューを先に**通し、人は *設計と意図* の確認に集中する
  - 報告例: 指摘の検出 **+60%**、人のレビュー時間 **−25%** <span class="tag amber">ベンダー系の数値</span>
- **Sphinx** (HN **253pt**): 出荷前に「AIが書いたコード」について**人間にクイズを出す**フック
  → 理解していないコードをマージしないための仕組み
- Claude Code の Code Review は**承認もブロックもしない**設計。判断はあくまで人間

> 現実: 調査した GitHub PR では、AIレビューbotが「無料枠の上限です」「時間切れで停止」と止まっている例が多数 → **運用とコストの設計が必要**

---

## ⑤ 並列化: サブエージェントと worktree

- **寄り道はサブエージェントに任せる**: 調査や周辺作業を別のコンテキストに逃がし、メインの文脈を汚さない
  - よくあるPR作業を `.claude/agents/*.md` に定義して自動化する (公式Tips)
- **複数エージェントを並列で動かす**
  - git worktree ＋ タブで、*担当をはっきり分ける* (Warp Docs)
  - 「Tmux and Claude Code: Sessions, Send-Keys, and the Ceiling」(HN **172pt**)
  - 状況ボードやタスクボードのOSSが続々登場 (Weatherdeck, Multica)
- 人間の役割は「**チェスの20面指し**のように、各エージェントの成果をレビューすること」(ForrestKnight, 33万再生)

---

## ⑥ モデルを使い分ける ／ ⑦ 権限を最小にする

<div class="cols">
<div>

### ⑥ モデルの使い分け
- 計画・重要な判断 → 上位モデル
- 実装 → 中位モデル
- 調査・情報収集 → 軽量モデル
- 「上位モデルの判断力を、**全ターン分の料金を払わずに**使う」(X上で複数の投稿)
- アイドル中のセッションも利用枠を消費している (@0xLagosaur)

<p class="note">※ 具体的なCLIフラグや設定は公式ドキュメントで要確認</p>

</div>
<div>

### ⑦ 権限は最小に
- `--dangerously-skip-permissions` の常用は危険 (@Anish114870)
  - ファイルシステム、環境変数、本番の秘密情報まで丸見えになる
- **使い捨てのサンドボックス**で隔離する
- 危険な操作は**人が承認**する (Cline の設計思想)
- 本番の秘密情報をプロンプトに貼らない

</div>

## アンチパターン

| やりがち | 代わりに |
|---|---|
| 雰囲気で任せきり (vibe coding) | **人が方向を示し**、AIに実装させる |
| 「〇〇を作って」の一言で済ませる | Plan → Spec → 小さなタスク |
| CLAUDE.md の肥大化 | 短いルール ＋ フック ＋ スキル |
| AIの出力を読まずにマージ | AIレビュー → 人間による意図の確認 |
| **コード行数で成果を測る** | リードタイム・レビュー時間・revert率 |
| 全権限で常時実行 | サンドボックス ＋ 承認ゲート |

> ForrestKnight:「AIとのペアプロが人間とのペアプロと違うのは、**変数名にケチをつけず、昼飯も食べない**ことくらい」

# Part 3　自分たちのPJへの導入

---

## 導入ロードマップ (案)

### Step 0 (1週目): 土台を作る
- AGENTS.md / CLAUDE.md を作る (ビルド・テスト手順、規約、禁止事項)
- 権限ポリシーを決める (サンドボックス、秘密情報の扱い)

### Step 1 (2〜4週目): 1人1エージェントで始める
- Plan → 実装 → **テストが通るまで任せる**
- AIのミスはルールに1行追記。週1回、学びを共有する

### Step 2 (2〜3ヶ月目): レビューを仕組みにする
- AIレビューをCIに組み込み、先に通す。フックでテストを強制する
- 慣れた人から worktree での並列運用を試す

## 何を測るか:「速く書けた」で満足しない

Harvardの調査と Claude Codeチームの目標から、**見るべきは流れと品質**

| 指標 | 確かめたいこと |
|---|---|
| PRリードタイム (作成からマージまで) | レビュー待ちの列が伸びていないか |
| 1PRあたりのレビュー時間 | 人の負荷が実際に下がっているか |
| revert率 ／ 障害件数 | **品質を犠牲にしていないか** |
| PRのサイズ (差分の行数) | 小さく分割できているか |
| AIの利用コスト | 予算の可視化 (JetBrainsでさえ「AI予算の行方を追うのに4日かかった」) |

<p class="note">導入前の数値を、今週中に記録しておくのがおすすめ</p>

---

## 明日からのチェックリスト

- [ ] リポジトリに **AGENTS.md / CLAUDE.md** を置き、git で管理する
- [ ] 最初は **Plan mode** で始める
- [ ] 指示に「テストを先に書き、通るまで直す」を含める
- [ ] AIのミスは、**ルールに1行**追記する
- [ ] 差分は**小さく**、1PR = 1タスク
