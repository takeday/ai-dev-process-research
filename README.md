# 生成AI開発プロセス 調査アーカイブ

2026年7〜8月に実施した、生成AI活用に関する調査の記録と、そこから導いた着手案。

> **本アーカイブは想定ケース（モデルケース）に基づく分析です。**
> **「Webシステムの基盤部品を提供する10名程度のチーム」という設定**を置き、そこへ業界調査の結果を突き合わせる形で書いています。
> 各文書は「対象チーム」への提言として一人称で書かれていますが、**実在の組織・個人・取引関係を記述したものではありません。**

想定ケースを固定したのは、「業界動向の羅列」ではなく**具体的な制約下での判断**として書くためです。制約（人数規模、ボトルネックの所在、既存資産）が変われば結論も変わります。

## 収集方法 — なぜこの設計にしたか

### 第1群：意図的に「採用実績の少ないもの」を狙った

出発点の要望が**「ドラスティックに開発現場を変えるアイデアを広く。採用実績が少ないものも対象に」**だったため、検索エンジンの標準的な挙動を意図的に無効化しました。

通常この種のツールは**エンゲージメントの高い（＝既に話題になっている）情報を上位に出します**。それは「採用実績の少ないアイデア」と正面から衝突するため、以下を行いました。

- 検索語の設計を調整し、**話題性による絞り込みが効かない状態**にした
- 各ランで**5本のサブクエリ**を並走させ、取得の母数を確保した（既定の1本では36件しか取れなかった）
- 期間を30日に保ち、**新しさ＝新規性**として扱った

**代償**: 無関係な情報が混入しています。第1群では、たとえば「background agent」という検索語がCSSの背景や身元調査の記事を拾っています。**約1〜2割はノイズ**と見てください。

### 第2群：新語彙の二次探索

第1群の結果から、**言及が1〜2件しかない造語・技法名**を抽出し、それを主題として再検索しました。「採用実績が少ない」を機械的に判定する方法として、**言及の少なさを指標にした**わけです。

これが最も有効でした。第1群で各軸1件ずつしか出なかった **Loop Engineering** が、二次探索では168件（うちYouTube 50件）。**実際には急拡大中の概念**で、第1群の時点では語の新しさゆえに埋もれていました。

副産物として、この分野の語彙が階層として整理されていることが分かりました。

```
prompt engineering → context engineering → harness engineering
　→ loop engineering → graph engineering
```

### 第3群：設計を反転させた

「採用実績の多いもの」を追加で調べる際、第1群と**逆の設計**にしました。

| | 第1群 | 第3群 |
|---|---|---|
| 話題性による絞り込み | 無効化（長尾を残す） | **有効化**（主流を残す） |
| 主戦場 | ソーシャル層 | **Web記事層**（企業技術ブログ） |
| 期間 | 30日 | **90日**（事例記事は発行頻度が低い） |

企業の全社導入事例は**技術ブログと公式ケーススタディにしか載らない**ため、この群ではソーシャル層を補助扱いにしています。

**設計上の失敗**: E1で検索語の起点を `enterprise` にしましたが汎用的すぎ、医療AI・ERP移行・地方議会の議事録まで混入しました（202件中およそ半分）。E2の `GitHub` は絞り込みとして機能しています。

### Web記事層の後追い取得

第1群・第2群の実行時、**Web検索の層が全ランで0件**でした。エンジン内蔵のWeb検索が機能していなかったため、後から**全15ランについてWeb記事層を個別に取得し、各レポート末尾に追記**しています。

`01` `02` の数値の多くは、実はこの後追い分から来ています。特に **DORA系のデータと企業事例は、ソーシャル層にはほとんど存在せず、Web記事層に集中していました**。

## 01 の要約 — 業界動向

**位置づけ**: 情報共有。対象チームへの適用は書いていない。想定15分。

### 押さえるべき3点

1. **制約は「コードを書く速度」から「コードをレビューする速度」へ移った。** 導入後、85%のチームがレビューを最大のボトルネックと回答。PRレビュー時間の中央値は前年比+441%
2. **複数のAIツールを使い分ける層が製品化された。** Databricksが Omnigent をOSS公開（2026-06-16、Apache-2.0）。Claude Code と Codex の切替が設定1行
3. **無人・スケジュール実行が公式機能になった。** Claude Code Routines。ただし前提条件が重い

### 本文の構成

- **語彙が5層に整理された** — prompt / context / harness / loop / graph engineering。「競合する技術ではなく積み重なった制御単位」。**Loop Engineering は2026年6月命名の新語**
- **無人・24時間実行** — 公式サポートと、運用上の必須要件4つ（リトライ、タイムアウト、多重起動防止、**プロンプトの完全指定**）
- **複数エージェント併用** — Omnigent、git worktree パターン。ただし「worktree は隔離境界ではない」という反証あり
- **仕様駆動開発の定着** — 2025年登場、2026年に主要8ツールが実装済み。「**AI支援開発は曖昧さのコストを劇的に引き上げる**」
- **効果測定（AI生産性のパラドクス）** — 個人の産出は激増（PR +98%）するが**組織デリバリー指標は横ばい**。コストはマージPRあたり$0.28〜$89.32
- **国内の状況** — ReadyForの社内調査（83%が生産性向上を実感、一方**66.7%が「並列作業が増えた」**）、delyの「**理解負債**」
- **反証・失敗事例** — 並列化が効かなくなる3条件、コスト暴走、CVE、評価の陳腐化

## 02 の要約 — 論点提起

**位置づけ**: 論点提起。**結論は出していない。会議で決める前提。** 想定20分＋議論。

### 前提を揺さぶる事実（8点）

| # | 事実 | 含意 |
|---|---|---|
| 1 | AI導入後、85%がレビューをボトルネックと回答。レビュー時間 +441% | 「レビューがボトルネック」は正しいが、**AIで自動的に緩和されない。最初に悪化する箇所** |
| **1b** | **94%がレビュー時点では高品質と評価。しかし82%が本番障害を経験** | **レビューは「詰まる」だけでなく「素通りする」。要員増強では解けない** |
| 2 | 国内事例で66.7%が「並列作業が増えた」、大半がコンテキストスイッチ負荷 | **利用量の純増は負荷の純増と区別がつかない** |
| 3 | 理解負債 — 文脈を共有しないレビュアーの負荷が増える | 基盤部品チームの構造は**この負債が最も溜まりやすい形** |
| 4 | 無人稼働の前提は「曖昧さゼロの入力」 | 要件Fixがボトルネックのままでは**空回りする** |
| 5 | 並列化が効くのはコード生成が制約のときだけ | 収穫逓減の3条件のうち**2つが該当** |
| **6** | **コード再利用 -70%、重複 +81%、レガシー改修 -74%**（6億2,300万件分析） | **社内のAI活用が進むほど、基盤部品チームの提供価値が侵食されうる** |
| 7 | 育成 — 使い方のパターンで理解度が40%未満〜65%以上まで開く | **アウトプットでは、育っている人と委譲しているだけの人を区別できない** |
| 8 | Uberが予算を4月に枯渇。Gartnerは40%超のプロジェクトが中止と予測 | コスト統制は技術課題ではなく**経営課題** |

### 提示した論点（5つ）

1. **目標は「開発を速くする」で正しいか** — 下げたいのは1件あたりの所要時間か、滞留件数か
2. **24時間稼働は今のタイミングで意味を持つか** — 今やる施策か、要件側が片付いた後か
3. **何を測るか** — トークン単価か成果単価か。分母が未決
4. **初級者の問題を教育で解くか仕組みで解くか** — 教育側にも打ち手はあるが、教える対象がツールではなく**対話パターン**
5. **作った部品が使われ続けるかを見る必要はないか** — 事実6を受けて

### 提示した選択肢（5つ・相互排他ではない）

| | 内容 | 性質 |
|---|---|---|
| **A** | レビュー側に投資（規約準拠の確認を4層に分散、Greptile等） | 生産性 |
| **B** | 要件・仕様側に投資（受入条件skillの本格化） | 生産性 |
| **C** | 実行基盤に投資（メタハーネス・無人実行） | 生産性 |
| **D** | 計測基盤を作り直す（利用量ベース→成果ベース） | 基盤 |
| **E** | 部品を「使わせる」ための情報設計 | **提供価値の維持** |

**Eだけ性質が違います。** A〜Dが「生産性を上げる」施策なのに対し、Eは「成果物が使われ続けるようにする」施策。新規部品作成でも保守でもない第三の業務にあたります。

### 会議で決めたいこと（7項目）

狙う対象 / 優先順序 / 計測の分母 / 24時間稼働の位置づけ / **部品の利用状況を指標に入れるか** / **選択肢Eを業務として位置づけるか** / **品質側の打ち手を今期に入れるか**

**時間制約のある項目が1つあります**: 部品の利用状況（インポート数・呼び出し箇所数）は**過去に遡れません**。測ると決めるならベースライン取得を先に始める必要があります。
