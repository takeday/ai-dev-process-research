## 1. 現状の確認

**チーム構成**: 10名程度（バックエンド・フロントエンド混成）。Webシステムの基盤部品チーム。

**業務の二本立て**: リリース済み部品の保守開発（不具合・機能改善）／新規部品作成。

**最大の課題**: 要望がそれなりの頻度で発生するため、**課題の件数が±でキープされ、減らない**。

**生産性が上がらない要因（現状認識）**:
1. 定型プログラムではなく、利用者の実装簡素化と保守性の考慮が要る
2. **要件整理のFixが各チームのサブリーダを通るためボトルネックになっている**

**現在の取り組み**:
- 勉強会の定期開催（初級者の習熟に差が出ている）
- OTelで利用量を計測、週次で推移確認（純増中）
- Jiraチケットの受入条件を深掘りするskillを試作・検証中（サブリーダのレビュー負荷軽減が目的）
- 仕様検討会議を録画しトランスクリプトを蓄積（skill精度向上のインプット）

## 2. 調査で出てきた、前提を揺さぶる事実

### 事実1: レビューのボトルネックは、AI導入で「解消」ではなく「悪化」する

| 出典 | 数値 |
|---|---|
| 業界調査（Moderne 他） | AI導入後、**85%のチームがコードレビューを最大のボトルネックと回答** |
| DORA 2025系 | PRレビュー所要時間の中央値 **+441%**（前年は+91%） |
| DORA 2025系 | マージされたPR **+98%**、しかし**組織デリバリー指標は横ばい** |
| DORA 2025系 | レビューなしでマージされたPR **+31%** |

**含意**: うちの「サブリーダがボトルネック」という認識は正しい。ただしそれは**AI活用によって自動的に緩和される種類の問題ではなく、むしろ最初に悪化する箇所**である。

### 事実1b: しかも、レビューは「詰まる」だけでなく「素通りする」【追加調査で判明】

| 出典 | 数値 |
|---|---|
| New Relic *State of AI Coding 2026* | **リーダーの94%が、AI生成コードを「レビュー時点では」人間のコードより高品質と評価** |
| 同 | **82%が過去6ヶ月にAI生成コード起因の本番障害を経験** |
| CloudBees（200名超） | **81%が本番問題の増加を報告** |
| CodeRabbit（470 PR分析） | AI生成コードのバグ密度は人間の **1.7倍** |
| 複数調査 | リリースは20%速くなり、**本番障害は23.5%増** |
| New Relic 系 | **86%が「シニアがコード修正に費やす時間が増えた」と回答** |

**含意（当初の整理からの修正）**: 問題は「レビューで弾けるが手が回らない」ではなく、**「レビューを通過してしまう」**という性質のものだった。

**したがって、レビュー要員を増やしても・レビューを速くしても、品質問題は解けない。** 本番相当の検証（テスト、段階リリース、可観測性）が別途要る。選択肢Aの位置づけがこれで変わる。

### 事実2: 「並列作業が増える」ことは、利用者にとってコストでもある

ReadyFor（社内12名・3ヶ月）のアンケート:
- 83%が生産性向上を実感、66%が1日1〜2時間短縮
- 一方で **66.7%が「並列作業が増えた」と回答し、その大半がコンテキストスイッチの負荷を訴えている**

**含意**: 利用量（OTelで見ている数字）の純増は、**負荷の純増と区別がつかない**。今の計測では、この2つを分離できない。

### 事実3: 「理解負債」— 個人の生産性向上がチームの負債になる

dely の記事が提示した概念。個人の体感では速くなるが、**実装の文脈を共有していないレビュアーの負荷が増える**。

**含意**: うちの構造（部品の保守性を考慮する必要がある／レビューがサブリーダに集中）は、この負債が最も溜まりやすい形をしている。

### 事実4: 無人・24時間稼働の前提条件は「曖昧さゼロの入力」

スケジュール実行されるエージェントは**途中で質問できない**。プロンプトを完全指定する必要がある。

**含意**: 要件整理のFixがボトルネックである限り、24h稼働させても**入力が枯れて空回りする**。順序が逆になっている可能性がある。

### 事実5: 並列化は、制約がコード生成速度にあるときしか効かない

収穫逓減に入る3条件のうち2つが、うちに該当している:
- **外部制約に「人間の承認」が明示されている** → サブリーダのFix
- **直列依存** → 要件が確定するまで実装できない

### 事実6: AI支援開発は「再利用」を減らす【本日の最重要事項】

GitClear / GitKraken が **2023〜2026年の実コード変更 6億2,300万件**を分析した結果:

| 指標 | 変化 |
|---|---|
| コード重複 | **+81%** |
| **コード再利用** | **-70%** |
| レガシーのリファクタリング | **-74%** |
| 機能的連結性（新規コードが既存関数を再利用する度合い） | **-35%** |
| エラーの隠蔽（想定外入力を握り潰す catch 等） | **+47%** |

分析元の要約:
> **「何かが欲しくなるたびに、AIはそれ用の新しいパッケージを作る。」**

**含意 — これは他人事ではない。**

うちの存在意義は「再利用可能な共通部品を提供し、利用者の実装を簡素化すること」である。上の数字が示しているのは:

- **利用者側のエージェントは、うちが用意した部品を使わずに、その場で同等のコードを書く**（再利用 -70%、機能的連結性 -35%）
- 同じ機能が方々に散る（重複 +81%）
- 既存部品の改善が進まなくなる（レガシー改修 -74%）
- 部品が返すエラーが利用側で握り潰され、不具合が見えにくくなる（エラー隠蔽 +47%）

理由も特定されている:
> **エージェントはコードを読める。しかし、あなたのコンポーネントが何をすべきものなのか、共有ライブラリの意図されたAPIがどうあるべきかは知らない。**

知らないから使わない。使わないから重複が増える。

**つまり、社内のAI活用が進むほど、うちの提供価値が侵食されうる。** 「部品を速く作れるか」だけを見ていると、この劣化は指標に出ない。

### 事実7: 育成は「アウトプットでは判定できない」【追加調査】

Anthropic の無作為化統制試験（n=52、主に初級者、Trioという未経験ライブラリでの実装課題）:

- AI支援群のクイズ平均 **50%** vs 手書き群 **67%**（**17ポイント差、文字評価で約2段階**、p=0.01）
- **最も差が開いたのはデバッグの設問**
- 完了時間はAI群が約2分速かったが、**統計的に有意ではない**（この課題では速くもなっていない）

**決定的なのは、使い方のパターンで結果が分かれたこと**:

| 使い方 | 理解度 |
|---|---|
| **AI委譲**（完了**最速**・エラー**最少**） | 40%未満 |
| AIに「解かせる」反復デバッグ | 40%未満 |
| 生成後に追加質問して理解する | 65%以上 |
| **概念的な質問しかしない／エラーは自力解決** | **65%以上・かつ全体で2番目に速い** |

**含意1**: 学習と速度はトレードオフではない。**良い使い方は速くかつ身につく。** 分岐点は「解かせるか、分からせるか」。

**含意2（管理上の警告）**: **アウトプットだけを見ていると、最も学んでいない人が最も優秀に見える。** 「AI委譲」群は最速・最少エラーだった。**OTelの利用量指標では、育っている人と育っていない人を区別できない。**

### 事実8: コスト統制は技術課題ではなく経営課題【追加調査】

| 事例 | 内容 |
|---|---|
| **Uber** | **2026年のAIコーディング予算を4月までに使い切った** |
| GitHub Copilot | 2026年6月の課金変更で、あるプロセスの**利用量が24倍に増える試算**。**予算上限到達で開発者全員がアクセス不能**（段階的劣化ではなく突然の全面停止） |
| Gartner予測 | **AIエージェント導入プロジェクトの40%超が2027年末までに中止**。理由は**コスト急増・ビジネス価値の不明確さ・リスク管理不足**（いずれも技術以外） |
| Gartner調査 | **企業の73%がシャドーAIを管理できていない**。一方で75%が部門選定ツールを何らかの形で容認 |

背景として明示されているのは**使われ方の変化**:
> チャットボット時代の利用量を前提にした料金感覚のまま、**エージェントが自律的にツールを呼び出す使い方に切り替わった。その結果、想定は桁単位で外れる。**

**含意**: ライセンスが組織から提供されており直接負担がないとしても、**トークン消費の実測値を今のうちに取っておく**ことが、将来の内製化・拡大・契約更改時の見積根拠になる。

## 3. 論点

### 論点1: 目標は「開発を速くする」で正しいか

課題件数が±でキープされている構造は、**開発速度ではなく流入量と確定速度で決まっている**可能性がある。

- 生成を速くしても、レビューと要件Fixで詰まるなら、件数は減らない
- 業界データ（PR +98% / 組織デリバリー横ばい）は、まさにこの現象を示している

**問い**: 我々が下げたいのは「1件あたりの所要時間」か、「滞留件数」か。両者は同じ施策では動かない。

### 論点2: 24h稼働は、今のうちで意味を持つか

「昼 Claude Code・夜 Codex」のような常時稼働は、技術的には既に手が届く（Claude Code Routines で公式サポート、Omnigent で切替は設定1行）。

しかし前提条件が「完全指定された入力」であり、うちのボトルネックはまさにそこにある。

また導入順序についての警告がある:

> 弱いループの上に build されたグラフは、より多くの場所で同時に壊れるだけ。

**問い**: 24h稼働は「今やる施策」か、「要件側が片付いた後の施策」か。先にやる合理性はあるか。

### 論点3: 何を測るか — トークン単価か、成果単価か

現在OTelで利用量を計測している。これは**分母の選択**が未決の状態にある。

> **「トークンあたりコスト」で測ると、AIを使わないことが報われる。**
> **「成果あたりコスト」で測ると、効率よく多く使うことが報われる。**

業界ベンチマークは既に「マージPRあたりコスト」で語られている（$0.28〜$89.32、中央値でPRあたり750万トークン）。

Claude Code の公式ダッシュボードは**「全マージPRに占めるClaude Code由来PRの割合」**を既に持っている。OTel側は accept/reject 率を取れる。

**問い**: 利用量の推移から、成果ベースの指標へ切り替えるか。切り替えるなら分母は何か（マージPR / クローズ課題 / リリース部品数）。

### 論点4: 初級者が追いつけない問題を、教育で解くか仕組みで解くか

勉強会を続けているが、初級者の習熟に差が出ている。

国内記事に共通して現れる問題設定は「**個人で使うClaude Code**」を「**チームで育てるClaude Code**」にすること。つまり個人スキルの底上げではなく、**規約・skill・ハーネス側に知識を移して個人差を吸収する**方向。

うちが試作中の受入条件skillは、既にこの方向の施策になっている。

**問い**: 教育投資と仕組み投資の比率をどう置くか。勉強会は継続するとして、その目的を「使えるようにする」から「仕組みへのフィードバックを集める」に変えるべきか。

**追加調査で分かったこと**: 教育側にも打ち手はある。ただし**教える対象がツールの機能ではなく「対話パターン」**である点が違う（事実7）。効果が確認されているのは、**manual-first**（先に手で書かせてから使わせる／自信+10.6%、知識ギャップ-16.1%）、**ピアラーニング**（形式研修単独より22%効果的）、**日常業務への埋め込み**。Microsoftの数万人規模の研究でも「初回利用はソーシャルなつながり経由で広がった」と一致している。

**補足の問い**: 初級者に不足しているのは**ツールの操作能力ではなく、AIの出力を評価する能力**である可能性が高い（初級者の生産性向上が15〜25%に留まる理由として明示されている／最も差が開いたのがデバッグ）。勉強会で「この生成結果は正しいか」を判定させる演習を入れれば、操作の問題か評価の問題かを切り分けられる。

### 論点5: 「作った部品が使われ続けるか」を見る必要はないか【新設】

事実6の通り、AI支援開発は**再利用を70%減らし、重複を81%増やす**。うちは共通部品を提供する立場なので、この劣化は**提供価値そのものの毀損**にあたる。

現在の指標（利用量、課題件数）では、この現象は見えない。

**問い1**: うちの成果指標に「部品が使われている度合い」を入れるか。候補は、基盤部品のインポート数・呼び出し箇所数の推移、部品と同等機能の重複実装の検出、部品のバージョン更新追随率。

**問い2**: 使わせるための施策（利用者側のエージェントが部品を正しく見つけて使えるようにする情報設計）を、うちの仕事として位置づけるか。**これは新規部品の作成でも保守でもない、第三の業務になる。**

**参考**: 業界では「エージェントは主要なAPI消費者の一種になりつつあり、**機械可読性が開発者体験と同等に重要**になる」と整理されている。前回調査のStripeの思想とも一致する — AIは「あらゆる言語を知っているが**ビジネス文脈を持たない**優秀な新人」であり、**与えるべきはドキュメント・サンプルコード・アーキテクチャパターン**。**この3点はうちが既に所有している資産**である。

## 4. 選択肢（並列に提示。相互排他ではない）

### A. レビュー側に投資する【追加調査で内容を修正】

**内容**: 規約準拠の確認を、サブリーダのレビューから**4つの層に分散**する。

| 層 | 執行タイミング | 性質 | 何を置くか |
|---|---|---|---|
| 1. 決定的検査（lint / formatter / 静的解析） | コミット・CI | **確実** | フォーマット、命名、インポート順、禁止API、複雑度上限 — **機械が判定できるものすべて** |
| 2. 規約ファイル（`AGENTS.md` 等） | **生成時** | 確率的 | アーキテクチャパターン、エラー処理方針、テストの書き方、「なぜそうするか」 |
| 3. AIレビュー（Greptile 等） | PR時 | 確率的 | 自然言語で書ける規約、文脈依存の判断 |
| 4. 人間レビュー | PR時 | 判断 | 設計判断、利用者への影響、仕様との整合 |

**現状は、本来1〜3層に置けるものが4層（サブリーダ）に集中している。** これが「規約準拠のレビューが足枷」の正体と見ている。

**重厚な規約は捨てる必要がない。** 業界の議論はむしろ「**書かれた規約のルネサンス — AIもマニュアルを読むから**」という方向で、既に規約を持っていることは有利な状態。ただし**形式は変える必要がある**（後述のリスク欄参照）。

**具体的な道具**: Greptile（**$30/席/月**、10名で月$300程度）。自然言語で書いた規約を毎PRで執行でき、**全エンジニアのPRコメントを読んでチーム標準を継続学習する**（サブリーダの暗黙知が、明示的に書き起こさなくても蓄積されうる）。独立ベンチマークでバグ検出率82%（GitHub Copilot 54%、CodeRabbit 44%）。AWSセルフホスト可。詳細は `../03-コーディング規約とAIレビュー.md`。

**根拠**: ボトルネックが実際にここにある（85% / +441%）。国内にも同型の取り組みがある（「レビュー結果を学習し、観点・Skill・自動検査へ昇格する仕組み」）。

**前提条件**: レビューで何を見ているかの言語化。現在サブリーダの頭の中にある。ただしGreptileの学習機能を使うなら、**全部を先に書き起こす必要はない**。

**測り方**: PRあたりレビュー所要時間、サブリーダのレビュー担当比率、差し戻し率、**AIレビュー指摘の対応率**（ノイズ化の検知に最重要）。

**リスクと限界（当初の整理から修正）**:

1. **これだけでは品質問題は解けない。** 事実1bの通り、AI生成コードはレビューを通過してしまう（94%が高品質と判定されるのに82%が本番障害）。**読むだけのレビュー強化には原理的な限界がある。** テスト・段階リリース・可観測性とセットにして初めて効く
2. **自然言語ルールの執行は確率的で、lint のような確実性はない。** 確実に守らせたいものは1層へ
3. **重厚な規約をそのままエージェントに渡すのは最も効かない形式。** 指示追従は確率的であり、**長いコンテキストに埋もれた規則ほど無視される。指示ファイルの先頭にある規則は、9章に埋もれた規則より確実に従われる。指示を増やしても信頼性は上がらない。** 規約の再フォーマット（重要度順に並べ替え、正例と誤例を併記、根拠を書く）が要る
4. 一次レビューをAIに任せすぎると「レビューなしマージ+31%」の側に倒れる
5. **規約ファイルはプロンプトインジェクションの攻撃面になる**（NVIDIAが緩和策の技術ブログを出す段階。jqwikというJavaライブラリに、エージェントへ「アプリの出力を削除せよ」と指示する記述が開示なく混入していた実例あり）

### B. 要件・仕様側に投資する（現行skillの延長）

**内容**: 受入条件skillの本格化。Planning Agent パターン（曖昧な記述に対しシニアが訊く質問を返し、エッジケースを表面化させ、検証可能な受入条件に変換）の実装。仕様駆動開発の部分導入。

**根拠**: 要件Fixが直列依存の起点。ここが詰まる限り下流の施策が効かない。SDDは2026年時点で主要8ツールが実装済みで、手法として枯れつつある。

**前提条件**: 蓄積中の議事録トランスクリプトが使える形か。**ただしこの調査では「議事録→実行可能な仕様」の先行事例がほぼ見つからなかった**。既存ツールは要約とアクション抽出が上限。**参照できる事例が乏しい＝自前で試行錯誤する領域**と見ておく必要がある。

**測り方**: チケットあたりの往復回数、要件Fixまでのリードタイム、サブリーダへのエスカレーション件数。

**リスク**: 仕様ドリフト（SDDの既知の失敗モード）。仕様と実装の乖離を検知する仕組みが別途要る。

---

### C. 実行基盤に投資する（メタハーネス / 無人実行）

**内容**: Omnigent 等のメタハーネス導入、Claude Code Routines による定型作業のスケジュール実行、worktree による並列実行の整備。

**根拠**: 技術的な障壁が急速に下がった（Databricks の OSS、切替は設定1行、無人実行は公式機能）。保守開発の定型部分は無人化の候補になりうる。

**前提条件**: 入力の完全指定（＝Bが先に要る）。リトライ・タイムアウト・多重起動防止の運用設計。

**測り方**: 無人実行で完了した課題の件数と、その差し戻し率。

**リスク**: セキュリティ（CVE-2026-59726）。コスト暴走（サブエージェント無限再帰の実例あり）。**この領域のツールは大半が数ヶ月以内に登場したもので、淘汰前の段階にある** — 採用するなら乗り換え可能性を前提にする。

---

### D. 計測基盤を作り直す

**内容**: 利用量ベースから成果ベースへ。Claude Code公式ダッシュボード（マージPRに占めるAI寄与PRの割合）とOTel（accept/reject率、コスト）の併用。ベースラインの確定。

**根拠**: 「導入と計測を初日から並行させ、ベースラインに対して追跡した組織が成果を出した」。現状は利用量の純増しか見えておらず、負荷増と成果増が分離できていない。

**前提条件**: 何を成果とするかの合意（論点3）。

**測り方**: これ自体が測り方の整備。

**リスク**: 計測が目的化する。また、AI起因コードの割合が上がるほどDORA指標単体は誤誘導的になるため、指標セットの設計が要る。**加えて、利用量指標では「育っている人」と「委譲しているだけの人」を区別できない**（事実7）。

---

### E. 部品を「使わせる」ための情報設計に投資する【新設】

**内容**: 利用者側のエージェントが、うちの部品を正しく見つけて・意図通りに使えるようにする。具体的には、各部品について「何を返すか」だけでなく**「いつ使うべきか」**を機械可読な形で書く。MCP を使って内部ドキュメントを構造化・クエリ可能な形でエージェントに露出する。サンプルコードとアーキテクチャパターンを、エージェントが読む前提で整備する。

**根拠**: 事実6（再利用 -70%、機能的連結性 -35%、重複 +81%）。原因は「エージェントが共有ライブラリの意図されたAPIを知らない」ことと特定されている。**うちの提供価値の毀損に直結する。**

**この選択肢の特徴**: A〜Dが「うちの生産性を上げる」施策なのに対し、Eは**「うちの成果物が使われ続けるようにする」**施策。**性質が違うので、他と並べて優先順位をつけるより、やるかやらないかを別途決める方が適切かもしれない。**

**前提条件**: 何を成果とするかの合意（論点5）。Aの規約整備と資産を共有できる（どちらも「文書を機械可読にする」作業）。

**測り方**: 基盤部品のインポート数・呼び出し箇所数の推移、部品と同等機能の重複実装の検出、部品のバージョン更新追随率。**先にベースラインを取らないと効果が見えない。**

**リスク**: 業界に先行事例が薄い領域（プラットフォームチーム×エージェントという組み合わせ自体が新しい）。試行錯誤が要る。また、うちの文書は下流のエージェントが読むため、**汚染された場合は利用者チーム全体に波及する**（Aのリスク5と同じ問題が、より広い影響範囲で現れる）。

---

## 5. この場で決めたいこと

1. **狙う対象** — 「1件あたりの所要時間」か「滞留件数」か。どちらを主指標にするか
2. **優先順序** — A〜Dのうち、今期に着手するものと、次の判断まで待つもの
3. **計測の分母** — 利用量ベースを継続するか、成果ベース（マージPR / クローズ課題）へ切り替えるか。切り替えるならベースライン取得をいつ始めるか
4. **24h稼働の位置づけ** — 今期の検討対象に含めるか、要件側が片付いた後の課題として置くか
5. **【新規】部品の利用状況を指標に入れるか** — 入れるなら、ベースライン取得を先に始める必要がある（後から遡れない）
6. **【新規】選択肢Eを、うちの業務として位置づけるか** — 新規部品作成・保守に次ぐ第三の業務になる。工数の出どころを決める必要がある
7. **【新規】品質側の打ち手を今期に入れるか** — レビュー強化だけでは解けないことが判明した（事実1b）。テスト・段階リリース・可観測性のどこから着手するか

## 6. 想定問答

**Q. 業界の数字はうちに当てはまるのか**
A. DORA/DX系の数値は主に海外企業の大規模調査。国内12名規模の事例（ReadyFor）でも「並列作業増・コンテキストスイッチ負荷」という同方向の結果が出ており、**現象の方向は一致している**。ただし数値そのものの一致は期待できない。**自チームのベースラインを取るまでは、方向の示唆として扱うのが妥当。**

**Q. 数値の出典は信頼できるか**
A. DORA Report 2025 と DX社の調査を、各社の技術ブログが要約したもの。**一次レポートは未確認**。意思決定の根拠にする場合は原典を当たる必要がある。

**Q. Omnigent を今すぐ入れるべきか**
A. 判断材料は揃っていない。公開から1ヶ月半（2026-06-16）、この領域は同種ツールが多数出ており淘汰前の段階。ライセンスは Apache-2.0、提供元は Databricks なので素性は悪くないが、**先に入れるべきは入力側（B）である可能性が高い**、というのが調査から読める順序。

**Q. 勉強会はやめるのか**
A. やめる根拠は出ていない。ただし国内記事に共通するのは「個人で使う → チームで育てる」への移行で、**個人スキルの底上げだけでは差が埋まらない**という認識。勉強会の目的を再定義する余地はある。

**Q. コストはどれくらい見ておくべきか**
A. 業界ベンチマークではエンジニア1人あたり月$200〜$600（シート＋トークン）。ライセンスが組織から提供されているため直接負担はないとしても、**トークン消費の実測値は今のうちに取っておく価値がある**（将来の内製化・拡大時の見積根拠になる）。

**Q. 失敗したケースはあるか**
A. ある。「AIエージェントを増やしたのに成果が-70%落ちた」（国内、X）、サブエージェント生成バグによる無限トークン消費と作業消失（GitHub, CRITICAL）、「1年前に使えないと判断した会社がその判定を維持している」（評価の陳腐化）。**並列化が効くのはコード生成が制約のときだけ**、という判定基準が複数ソースで一致している。

**Q. うちの規約は捨てるべきなのか**
A. 逆。業界の議論は「**書かれた規約のルネサンス — AIもマニュアルを読むから**」という方向で、規約を既に持っていることは有利。「**コードベースが一貫したパターンに従っているとき、AIは力の増幅器になる。従っていないとき、混沌の増幅器になる**」。ただし**形式は変える必要がある** — 長い文書の後半は無視されるため、重要度順の並べ替え、正例と誤例の併記、根拠の明記が要る。

**Q. Greptile はすぐ入れられるのか**
A. 判断材料は揃っている方だが、先に決めることが3つある。(1) 対象システムのコードをSaaSに送れるか（送れないならAWSセルフホスト、またはMira等のOSS）(2) lint等の決定的検査で落とせるものを先に落とすか（全部Greptileに載せるのは非効率）(3) 指摘の対応率をどう測るか（ノイズ化したら価値がゼロになる）。**まず1リポジトリで規約ルールを数本だけ書いて精度を見るのが妥当。**

**Q. 再利用が減るという話は、うちにも本当に当てはまるのか**
A. 6億2,300万件のコード変更という規模の分析なので、傾向としての信頼度は高い。ただし**うちで実際に起きているかは未確認**。確認方法はある — 基盤部品のインポート数・呼び出し箇所数の推移を見ればよい。**ただし過去に遡れないので、測るなら早い方がいい。** これが「決めたいこと5」の理由。

**Q. 初級者にはAIを使わせない方がいいのか**
A. **業界内でも決着していない。** 「初級者から先に展開すべき」（初級者に利益があり経験者にはむしろ足を引っ張る）という分析と、「慎重に」（理解度17ポイント低下、生産性向上は15〜25%に留まる）という分析が両方ある。ただしAnthropicの研究が示すのは、**使い方のパターンが結果を支配する**ということ。であればこの対立は「使い方を規定しているかどうか」の差である可能性がある。**自チームでの観察を優先すべき領域。**

**Q. 勉強会をどう変えればいいのか**
A. やめる根拠は出ていない。変えるとすれば目的。(1) 教える対象を**ツールの機能から対話パターンへ**（「解かせる」ではなく「分からせる」問いかけ方）(2) 講義形式に**ピア形式と日常業務への埋め込みを併用**（ピアラーニングが22%効果的）(3) 初級者は**持ち道具を段階的に**（補完 → 対話 → エージェント）。詳細は `../04-イネーブルメント-初級者の育成.md`。

**Q. AI生成コードの保守性について、他社はどう判断しているのか**
A. 極端な例では、オープンソースゲームエンジンの **Godot がAI生成コードの寄与を受け付けない方針に転換**した（2026年7月、Hacker Newsで561ポイント）。理由は「**AIのヘビーユーザーが、自分のコードを修正できるほど理解しているとは信頼できない**」。社内チームで同じ手段は非現実的だが、**「書いた人が説明・修正できること」を要件として明示する**部分は移植できる。
